# Инструкции и правила проекта (Мой ИМЭС)

## 1. Процесс работы (Review Before Action)
* **Сначала план и ревью, потом код:** Когда пользователь озвучивает идею или задачу, **НЕ** бросаться сразу редактировать файлы. Сначала кратко и понятно расписать:
  - Что именно планируется сделать и в каких файлах.
  - Как это будет выглядеть в интерфейсе.
  - Дождаться подтверждения («добро», «го») перед внесением изменений.
* **Честная критика и здравый смысл:** Если идея пользователя или подход — плохие, неэффективные или неудобные («полная фигня»): прямо сказать об этом, аргументировать почему и предложить 1–2 качественные альтернативы. Цель — создать идеальное приложение для всех студентов, а не просто слепо пилить всё подряд.

## 2. Уровень коммуникации и тон
* **Понятный язык без снобизма:** Не предполагать, что пользователь глубокий senior-разработчик. Объяснять простым языком, на пальцах.
* **Баланс подробности:** Никакой «воды», лекций или библейских простыней текста. Достаточно ёмко, понятно и по существу. Язык общения — русский.

## 3. Архитектура: разделение UI и Данных (Подготовка к 1С)
* **Абстракция от бэкенда:** Базой данных вуза является **1С**, а текущий Moodle/ЭИОС — временный источник. В будущем возможен переезд на прямое API 1С.
* **Правило изоляции UI:**
  - Экраны (`lib/features/**/screen.dart`) и виджеты должны знать **только** о моделях данных и интерфейсах репозиториев (`ScheduleRepository`, `GradesRepository` и т.д.).
  - Никаких прямых вызовов парсинга HTML, кук, сетевых запросов и Moodle-специфики внутри UI-кода.
  - Вся работа с сетью и хранилищем спрятана внутри слоя данных (`repository.dart` / `client.dart`), чтобы при переезде на 1C можно было заменить источник данных в одном месте без переписывания интерфейса.

## 4. Стандарты кода (Flutter / Dart)
* **Тактильный отклик (Haptic):** Любые нажатия кнопок, вкладок, карточек и свитчей вызывать строго через `AppHaptics` (`lib/ui/app_haptics.dart`), чтобы уважался пользовательский тумблер в Настройках.
* **Современный синтаксис:** Использовать `.withValues(alpha: ...)` вместо устаревшего `.withOpacity(...)`.
* **Стабильность виджетов:** Не ломать дерево и типы корневых элементов при анимациях и переходах, чтобы избегать ошибок жизненного цикла `InheritedElement`.
* **Верификация:** После реализации фичи или фикса обязательно запускать `flutter analyze` по изменённым модулям — в коде должно быть 0 ошибок.

## 5. Релизы и документация (Версионирование и синхронизация README)
* **Формат заголовка коммита:** В заголовке (первой строке) релизного коммита указывать строго краткий формат: `release: vX.X.X`. Всё подробное описание изменений на русском и английском помещать исключительно в тело (body) коммита, чтобы список коммитов на GitHub оставался чистым и аккуратным.
* **Автоматическое версионирование:** При каждом релизе/пуше обновления версия приложения повышается на `+0.0.1` (и build number `+1`), если пользователь явно не озвучил иной номер версии.
* **Обязательное обновление README при пуше:** При любом обновлении версии обязательно актуализировать документацию:
  - Версию и дату в `pubspec.yaml`, `README_RU.md` и `README_EN.md`.
  - Актуальные пункты Roadmap и списка возможностей (включая скриншоты).
  - Ссылки на установку (Android APK / iOS Sideload).

## 6. Безопасность и терминальные команды
* **Категорический запрет (Hard Ban):**
  - **Никакого ADB и устройств:** Категорически запрещены `adb install`, `adb uninstall`, `adb shell`, `adb reboot` или `flutter run -d <device>` на реальных устройствах. Телефон не трогать — пользователь устанавливает APK на смартфон исключительно сам.
  - **Никаких деструктивных сбросов Git:** Запрещены `git push --force` (`-f`), `git reset --hard`, `git clean -fd` (риск безвозвратной потери кода).
* **Строго по согласованию (только после «коммить», «пушь», «добро»):**
  - `git commit` и `git push` — коммиты и пуши в удалённый репозиторий выполняются ассистентом, но **строго** после показа изменений и явного подтверждения от пользователя.
  - Удаление существующих файлов и папок проекта (`rm`, `del`, `Remove-Item`).
  - Очистка кеша сборки (`flutter clean`) — только если сборка сломалась и пользователь согласовал.
* **Разрешено выполнять самостоятельно:**
  - Сборка артефактов: `flutter build apk` (и другие локальные таски сборки).
  - Проверка качества и тесты: `flutter analyze`, `flutter test`.
  - Управление зависимостями: `flutter pub get`.
  - Инспекция Git (read-only): `git status`, `git diff`, `git log`, `git branch`.
  - Поиск и анализ файлов проекта, чтение логов и локальных конфигов.
